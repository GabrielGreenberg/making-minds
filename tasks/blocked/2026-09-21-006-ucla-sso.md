## Description
Everything around SSO is done: `MM_AUTH_MODE=sso` + `MM_SSO_LOGIN_URL` make the login
screen show one "Sign in with UCLA" button (it reads `GET /api/auth/config`), sessions and
routes are provider-agnostic. `SsoAuthProvider.authenticate` in `server/src/auth.ts` is one
honest TODO: validate the assertion, map attributes to `{email, name}`, take the role from
the roster, upsert, return the row.

## Done when
- A real UCLA login round-trips into a bearer session on the pilot box; roster gating and
  roles unchanged; `authCheck` gains an SSO decision-table section with a fake IdP.

## Design
Protocol-dependent (see Questions). Either way: a callback route, assertion validation
against IdP metadata, attribute mapping, then the existing upsert. Keep the provider seam;
no frontend rebuild.

**Consequence from 018 (2026-09-24):** `tasks/tools/feedback.mjs` signs in as an instructor
with an email + password (`secrets/feedback.env`) through `POST /api/auth/login`. Once the
pilot runs `MM_AUTH_MODE=sso` that path is gone: give the pipeline a server-issued,
revocable key (instructor-scoped, feedback read + triage only) and switch the script to it
in the same change, or the feedback pull stops working the day SSO ships.

## Verify
`authCheck` with a stub IdP; a real login is owed (needs UCLA's test IdP).

Note (catch 2026-09-23): the real Fall 2026 class list shows 37 of 87 emails are personal
(non-UCLA) addresses, so SSO must match the roster by UID, not by email. See task
2026-09-23-036 (identity by UID), which should land first; the attribute to ask UCLA IT for is
the UID (University ID), alongside the logon email.

## Questions
1. Which protocol does UCLA IT offer this app: Shibboleth/SAML, or OIDC (CAS)? Is there a
   registered service provider / client id yet, and who is the contact?
2. Is a test IdP available, and which attributes carry email and display name?
3. Should students who authenticate via SSO but aren't on the roster get the access-request
   flow, or a plain refusal?
