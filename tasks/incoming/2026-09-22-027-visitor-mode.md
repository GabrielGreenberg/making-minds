## Description
Gabriel: let people use the sandbox without logging in ("visitor mode"), easy and prominent
because many visitors will want it; a new user is led into the visitor path by default, while
someone who has signed in before is signed in again automatically or led to sign in. Bells and
whistles (saving/loading a worksheet as a file) come later — task 028. Provenance: chat, catch
session 2026-09-22.

### What the app does today
- **Everything is gated on a user.** `AuthGate` (`app/src/auth/AuthGate.tsx:20–40`) renders the
  login screen whenever `user` is null and only then starts routing (`initRouting`,
  `routing.ts:185–200`), so `#/sandbox` is never even applied before sign-in. In remote mode
  `HealthGate` (`auth/HealthGate.tsx:23–52`) sits in front of all of it and shows "The course
  server can't be reached" until `/api/health` answers — nesting `HealthGate > AuthProvider >
  AuthGate > App` (`main.tsx:19–29`).
- **Session restore already exists.** Local: the toy account id under `mm:auth:current` is
  restored synchronously (`authProvider.tsx:65`, `accounts.ts:24–34`). Remote: the bearer token
  under `mm:auth:token` → `me()` → user (`authProvider.tsx:139–203`; a 401 clears the token, any
  other failure keeps it but boots logged out). `logout()` clears both (`:79–86`, `:273–279`).
- **The sandbox needs no identity and no server.** It is the editor branch of `App.tsx:65–85`
  (no `PageShell`), entered by `enterSandbox` (`store.ts:1629–1655`), autosaved as ONE
  per-browser blob `making-minds-autosave` (`store.ts:3760`, `:3911`, loaded at import
  `:4072–4157`) in both modes — it never touches `WorkbookStore` or the API.
- **Chrome assumes a user.** `MenuBar.tsx:79–85` always renders Feedback and Log out;
  `FeedbackPanel.tsx:68` calls `getCurrentUserEmail()`, which throws when logged out
  (`authProvider.tsx:303–312`), and `POST /api/feedback` requires a session
  (`server/src/app.ts:594`). `PageShell`/`SessionControls`/`StudentLayout` already tolerate a
  null user (`SessionControls.tsx:17`, `StudentLayout.tsx:22–23`). `Role` is
  `'student' | 'instructor'` (`accounts.ts:9`); no guest principal exists anywhere.

### Root cause — the class
Identity is binary (a user or nothing) and access is decided once, globally, at the top of the
tree — so a surface that needs no identity (the sandbox) is still locked behind sign-in and,
remotely, behind server health. The fix is to make **access a property of the route** and to
give the app a third principal, the **visitor**.

## Done when
1. **Principal.** `AuthContextValue` exposes `principal: { kind: 'visitor' } | { kind: 'user',
   user: AuthUser }` (or `user: AuthUser | null` plus a derived `isVisitor`) — a visitor is a
   first-class state, not "loading" and not "logged out".
2. **Route access.** `routing.ts` gains a pure `routeAccess(route): 'public' | 'signed-in' |
   'instructor'` — `sandbox` is public; home/grades/assignment need sign-in; instructor routes
   need the instructor role (as `InstructorGate` does today). Routing starts at boot for
   everyone; `AuthGate` becomes a per-route gate: a public route renders for a visitor, a
   signed-in route shows the sign-in screen and returns to the requested route after sign-in
   (a deep link to `#/a/hw1` still works — that guarantee is kept, `AuthGate.tsx:12–18`).
3. **Landing.** On boot with no session: a browser with **no trace** of a previous sign-in (no
   `mm:auth:current`, no `mm:auth:token`) at `#/` is sent to `#/sandbox` as a visitor; a
   browser that HAS a trace but whose session no longer restores (expired/401 token) lands on
   the sign-in screen. With a restorable session, boot is unchanged (Home). After an explicit
   Log out: the sign-in screen.
4. **Sign-in screen.** Offers "Continue as a visitor → Sandbox" as prominently as Sign in, in
   both modes and in every remote pane (password / SSO / dev).
5. **Visitor chrome.** In the sandbox a visitor sees a "Visitor" tag and a **Sign in** button
   where the name chip / Log out are; Feedback is hidden for visitors (the server would 401);
   a one-line dismissible banner says "You're in the sandbox as a visitor — PHIL 133 student?
   Sign in." The Home nav item is not offered to a visitor; page surfaces (if reached) show
   Sandbox + Sign in.
6. **Remote mode without the server.** The sandbox loads and works while `/api/health` fails;
   the health screen appears only when a signed-in route or the sign-in screen is requested
   (HealthGate moves inside the route gate, or gates only those branches).
7. **Nothing else changes for signed-in users**: submit, feedback, grades, freezing,
   instructor gating, the per-browser sandbox autosave (a visitor who later signs in keeps the
   sandbox they built — same key).
8. **Gates.** A headless pin for `routeAccess` and the landing decision (a small
   `routingCheck.ts` in `npm run check`, or a section in `navResetCheck`); `themeCheck` and
   `remoteStoreCheck` stay green (no grader or answer JSON enters the visitor path).

## Design
- **deepFix (recommended):** principal + route-level access + landing rule, as above. Retires
  the class: any future public surface (a textbook demo page, a shared circuit link) is one
  `routeAccess` entry, and the sign-in screen stops being a wall in front of the whole app.
  Seams: `src/auth/` (provider, gate, login screen), `routing.ts` (the `Route` union already
  is the one place navigation is defined), `PageShell`/`MenuBar` (chrome by principal). No
  store, engine or storage change; the sandbox blob is untouched.
- **surgicalFix:** a "Continue as visitor" button that logs in a fake local account
  `{ role: 'student', email: 'visitor@…' }`. Rejected: it leaks into submit/feedback/journal
  paths keyed by email, needs the server up in remote mode, and confuses the roster.
- **Assumptions recorded at intake (Gabriel to confirm; none blocks starting):**
  (a) unknown browsers land STRAIGHT in the sandbox (with the banner), not on a welcome page
  with two buttons; (b) Feedback is hidden for visitors rather than accepted anonymously;
  (c) in remote mode the sandbox is usable while the course server is down.
